# ACIDBLOOD - Project Rules

Godot 4.7.1 (Mobile renderer), typed GDScript, portrait 720×1280. Gameplay is 2D
on the X/Z plane (Y up): enemies advance toward +Z where the defended objective
sits.

## Product identity
- The public project identity is `ACIDBLOOD`. Do not use legacy prototype
  naming in player-facing content, data labels, docs, tools, or process.
- The theme source of truth is `docs/ACIDBLOOD_DIRECTION.md`. Read it before
  naming stages, enemies, towers, VFX, environments, UI mood, or art tasks.
- ACIDBLOOD is late-1980s industrial contamination, not medieval fantasy and
  not clean neon cyberpunk. Favor analog machines, CRT-era infrastructure,
  chemical industry, concrete, steel, rust, fluorescent light, biological
  contamination, and corporate/industrial aftermath.
- Prototype visuals should already point in that direction when touched:
  simple industrial forms, restrained materials, functional color accents,
  readable silhouettes, and VFX that communicates physical behavior.
- Do not perform a broad rename/refactor just for theme. Rename player-facing
  labels and data as they become relevant; keep stable internal code names
  until changing them has real engineering value.
- Player-facing naming must stay globally consistent once a term is chosen.
  Current visible vocabulary standard:
  - defended objective: `Barricade`
  - base tower units: `Bolt Turret`, `Cannon Turret`, `Frost Turret`
  - branch cards: `Branch: <name>`
  - UI/game text should prefer short functional wording over mixed thematic
    synonyms when both refer to the same gameplay object
- Do not mix old and new visible names for the same thing. If one player-facing
  term changes, update all affected visible copy in cards, HUD, progression,
  and shell screens within the same slice unless there is a deliberate design
  reason not to.

## Architecture invariants
- Three layers, keep them separate:
  - `core/` — game rules. RefCounted/static only, NO Node or scene references.
    Must stay runnable headless (tests and future balance simulator).
  - `data/` — Resource classes (`data/types/`) + `.tres` content. All balance
    numbers live here, never inline in gameplay code.
  - `game/` + `shell/` — Godot runtime/presentation. May read core/data; rules
    changes go in core, not here.
- All gameplay RNG derives from the run seed via `DetRNG.derive(seed, salt, i)`.
  Never call `randf()`/`randi()` globals for gameplay decisions.
- Spawn randomness stays behind `Battle.roll_spawn_x()` so wave code has one
  source of truth for lane spread.
- Every combat number resolves through `Battle.stat(path, base)` (stat paths
  like `guardian.damage`, `turret.bolt.damage`, `fortress.max_hp`).
- Cards are data composing `CardEffect` ops (ADD_STAT / MULTIPLY_STAT /
  UNLOCK_TURRET / HEAL_FORTRESS). Do not create per-card scripts. Extend the
  op vocabulary only when a card genuinely cannot be expressed.
- Draft offers should avoid dead choices when the runtime context is known.
  Example: pure-heal cards should not appear when the fortress is already at
  full HP.
- Early-run draft quality matters more than pure randomness. Keep light
  guardrails such as guaranteeing a structural option (`Build`) in the first
  drafts when available and avoiding offers that collapse into a single
  category when valid alternatives exist.
- Prefer real-game patterns over invented abstractions. When in doubt, use
  established tower-defense or strategy-game practices, keep backend logic
  simple and data-driven, and let the front end carry clarity, responsiveness,
  and beauty rather than compensating with clever but unnatural systems.
- Prefer keyboard-first interaction for battle flow. Draft choice, slot
  placement, and confirm actions should work cleanly with arrows plus
  `Space`/`Enter` as the primary path; mouse/touch can remain as fallback, but
  the minimum control set should stay small and mobile-friendly.
- When a spatial choice can be misread from world axes alone, make the scene
  itself the source of truth: number the pads/slots in the level, validate the
  reading from the gameplay camera, and do not rely on inferred front/back or
  left/right ordering.
- One script per system, not per variant: enemy/turret archetypes are `.tres`
  entries, never new scripts, unless behavior truly differs.
- Stages are data. `data/stages/*.tres` is generated by
  `tools/gen_stages.gd` — edit that script and rerun it; do not hand-edit
  stage `.tres` files.

## Validation
- Canonical local suite entry point: `tests/acidblood_suite_runner.tscn`.
- Shared suite logic: `tests/run_tests.gd`.
- MCP-discovered suite alias: `tests/test_acidblood.gd`.
- `./tools/validate.sh` is still the project-wide validation entry point, but
  on macOS its headless smoke path is known to be unstable in Godot 4.7.1 and
  may fail in the engine before the game code runs. Treat that failure as an
  environment/engine issue unless the editor/runtime path shows a real gameplay
  regression.
- Before considering gameplay work done, validate the change in the live
  editor/runtime path through Godot AI MCP. Use `./tools/validate.sh` as an
  additional check when it is behaving on the current machine.
- Validation hierarchy:
  - editor/runtime MCP = source of truth for gameplay behavior
  - `./tools/validate.sh` = secondary safety net
  - macOS headless smoke crash = environment issue until runtime proves otherwise
- Balance overview: `godot --headless --path . --script res://tools/balance_report.gd`.
  Use it before tuning numbers: it prints shared geometry / combat floors,
  guardian + enemy + turret bases, cards, permanent upgrades, and per-stage
  wave pacing (`enemies`, `xp`, projected `lvl_ups`).
- For every Godot task, use the Godot AI MCP workflow first so the editor and
  runtime validate the change, not just the raw script text.
- If a local headless smoke fails with a Metal/ZSTD or similar engine crash on
  macOS, do not block gameplay iteration on that result alone. Prefer a live
  editor/runtime check, then rerun headless on a more stable environment when
  you need CI-grade confirmation.
- When delegating to another coding agent, make it read the project docs first,
  ask for a project analysis and one execution plan before edits, and keep it
  inside the documented product direction instead of inventing new systems.

## Godot editing workflow
- Prefer Godot/MCP for scene-oriented work when the operation is supported:
  inspect the project, run the scene, catch runtime errors, and save scene
  changes through Godot-aware tooling instead of relying only on raw `.tscn`
  edits.
- Use `.gd` edits for logic, rules, and text behavior; use scene operations for
  layout, node hierarchy, and presentation structure whenever practical.
- After scene/UI work, validate in both ways:
  - run the relevant scene/project through Godot/MCP to catch runtime/editor
    issues
  - run `./tools/validate.sh` to keep headless coverage green
- Manual `.tscn` editing is still acceptable when MCP does not expose the
  needed operation, but it should be the fallback, not the default.

## Conventions
- 1 unit = 1 m, +Y up, -Z model forward, origins at base/feet
  (see `docs/ASSET_CONTRACT.md` before importing GLBs).
- UI target is portrait `720x1280`, with desktop test override currently
  narrower than target. Draft and battle UI should size from the live viewport,
  not from fixed widths larger than the available screen space.
- Prefer nested `Container` layouts over manual positioning for UI. For tall
  portrait overlays that can exceed the safe vertical space, prefer
  `ScrollContainer` + `VBoxContainer` instead of assuming all content fits.
- Apply the same rule to shell screens (`Home`, `Campaign`, `Result`): use
  container-first layout, add scroll where content can grow, and size grids for
  portrait readability before desktop convenience.
- Placeholder models are generated from data (shape/color/scale); a
  `model_scene` `PackedScene` export on the data resource replaces them without
  touching gameplay scripts.
- Art production is incremental, not a late global pass. Any meaningful visual
  or imported asset change must be judged from the real gameplay camera and
  must preserve collision, footprint, target points, sockets, node names, and
  runtime ownership.
- Establish reusable art rules only after evidence across representative
  assets. For a local asset change, apply at most the next durable improvement
  (scale, silhouette, pivot, material reuse, or readability); defer final
  texturing, bespoke wear, advanced VFX, and hero polish while gameplay is
  unstable.
- Save files are versioned JSON in `user://`; automated runs must use a
  scratch `save_path`, never the player save.
