# Bastion Vale — Project Rules

Godot 4.6 (Mobile renderer), typed GDScript, portrait 720×1280. Gameplay is 2D
on the X/Z plane (Y up): enemies advance toward +Z where the fortress sits.

## Architecture invariants
- Three layers, keep them separate:
  - `core/` — game rules. RefCounted/static only, NO Node or scene references.
    Must stay runnable headless (tests and future balance simulator).
  - `data/` — Resource classes (`data/types/`) + `.tres` content. All balance
    numbers live here, never inline in gameplay code.
  - `game/` + `shell/` — Godot runtime/presentation. May read core/data; rules
    changes go in core, not here.
- All gameplay RNG derives from the run seed via `DetRNG.derive(seed, salt, i)`.
  Never call `randf()`/`randi()` globals for gameplay decisions.
- Spawn randomness stays behind `Battle.roll_spawn_x()` so wave code has one
  source of truth for lane spread.
- Every combat number resolves through `Battle.stat(path, base)` (stat paths
  like `guardian.damage`, `turret.bolt.damage`, `fortress.max_hp`).
- Cards are data composing `CardEffect` ops (ADD_STAT / MULTIPLY_STAT /
  UNLOCK_TURRET / HEAL_FORTRESS). Do not create per-card scripts. Extend the
  op vocabulary only when a card genuinely cannot be expressed.
- Draft offers should avoid dead choices when the runtime context is known.
  Example: pure-heal cards should not appear when the fortress is already at
  full HP.
- Early-run draft quality matters more than pure randomness. Keep light
  guardrails such as guaranteeing a structural option (`Build`) in the first
  drafts when available and avoiding offers that collapse into a single
  category when valid alternatives exist.
- One script per system, not per variant: enemy/turret archetypes are `.tres`
  entries, never new scripts, unless behavior truly differs.
- Stages are data. `data/stages/*.tres` is generated by
  `tools/gen_stages.gd` — edit that script and rerun it; do not hand-edit
  stage `.tres` files.

## Validation
- `./tools/validate.sh` must pass before considering work done. It runs
  import/parse checks, `tests/run_tests.gd` (headless, no framework), and two
  battle smoke runs (`--smoke` user arg, isolated save file).
- Balance overview: `godot --headless --path . --script res://tools/balance_report.gd`.
  Use it before tuning numbers: it prints shared geometry / combat floors,
  guardian + enemy + turret bases, cards, permanent upgrades, and per-stage
  wave pacing (`enemies`, `xp`, projected `lvl_ups`).

## Godot editing workflow
- Prefer Godot/MCP for scene-oriented work when the operation is supported:
  inspect the project, run the scene, catch runtime errors, and save scene
  changes through Godot-aware tooling instead of relying only on raw `.tscn`
  edits.
- Use `.gd` edits for logic, rules, and text behavior; use scene operations for
  layout, node hierarchy, and presentation structure whenever practical.
- After scene/UI work, validate in both ways:
  - run the relevant scene/project through Godot/MCP to catch runtime/editor
    issues
  - run `./tools/validate.sh` to keep headless coverage green
- Manual `.tscn` editing is still acceptable when MCP does not expose the
  needed operation, but it should be the fallback, not the default.

## Conventions
- 1 unit = 1 m, +Y up, -Z model forward, origins at base/feet
  (see `docs/ASSET_CONTRACT.md` before importing GLBs).
- UI target is portrait `720x1280`, with desktop test override currently
  narrower than target. Draft and battle UI should size from the live viewport,
  not from fixed widths larger than the available screen space.
- Prefer nested `Container` layouts over manual positioning for UI. For tall
  portrait overlays that can exceed the safe vertical space, prefer
  `ScrollContainer` + `VBoxContainer` instead of assuming all content fits.
- Apply the same rule to shell screens (`Home`, `Campaign`, `Result`): use
  container-first layout, add scroll where content can grow, and size grids for
  portrait readability before desktop convenience.
- Placeholder models are generated from data (shape/color/scale); a
  `model_scene` `PackedScene` export on the data resource replaces them without
  touching gameplay scripts.
- Save files are versioned JSON in `user://`; automated runs must use a
  scratch `save_path`, never the player save.
